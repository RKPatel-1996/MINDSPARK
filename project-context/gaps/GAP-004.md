# GAP-004 - Review Submission Can Be Lost After UI Advancement

Status: OPEN

Date: 2026-09-26

Source: `DISC-002`, finding `MSR-01`

Severity: High

## Observation

`ReviewService.submitReview()` can return success before the underlying ReviewEvent repository append has reached its terminal result.

The Review UI advances after the service promise resolves.

If repository persistence later fails, the pending event can be removed after the answer state and direct retry opportunity have already been discarded.

## Why this matters

MindSpark review history is authoritative scheduler evidence.

A user must not be shown successful progression when the corresponding review can subsequently disappear without a recoverable acknowledgement or retry path.

This can cause durable history to diverge from what the user believes was recorded.

## Existing coverage limitation

Current duplicate-submission protection is strong.

Current UI failure tests simulate `ReviewService.submitReview()` itself rejecting. They do not exercise the actual path where the service has already returned and the repository append later fails.

## Required handling

Resolve through a bounded work item covering:

- ReviewService persistence/acknowledgement semantics;
- pending overlay behavior;
- UI advancement and retry state;
- real repository-rejection integration coverage;
- preservation of responsive offline queued-write behavior;
- preservation of duplicate-activation protection.

## Scope boundary

Do not combine this gap with:

- Firestore ReviewEvent schema-rule hardening;
- import uniqueness;
- query-scaling redesign;
- accessibility work;
- deployment.
