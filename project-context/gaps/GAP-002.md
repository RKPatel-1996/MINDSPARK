# GAP-002 - Oversized Single Production JavaScript Bundle

Status: RESOLVED_PENDING_PROMOTION
Date: 2026-09-26

## Observation

The canonical production build currently emits essentially the application as one large JavaScript bundle rather than using deliberate application-level code splitting.

WORK-007 measured:

- main JavaScript chunk: approximately 1,930.59 kB minified;
- gzip size: approximately 527.27 kB;
- Vite emits its chunk-size warning for bundles above 500 kB;
- Vite recommends dynamic `import()` or `build.rollupOptions.output.manualChunks`;
- the generated PWA precache contains approximately 2.39 MiB of assets;
- repository inspection found no application-level route/view lazy loading or explicit manual chunk strategy.

The production build still succeeds. This is a performance and packaging gap, not a demonstrated correctness failure.

## Impact

A large single application chunk can increase:

- initial JavaScript transfer cost;
- browser parse/compile work;
- memory pressure on lower-powered devices;
- application-shell update payload;
- the amount of application code that must be fetched before unrelated surfaces can execute.

The effect should be measured rather than assumed to be user-visible on every device.

## Proposed handling

Address in a separate governed performance work item rather than WORK-007.

That work should:

1. establish a reproducible before-state bundle baseline;
2. identify the largest contributors to the main chunk;
3. evaluate route/surface-level lazy loading and/or deliberate vendor chunking;
4. preserve HashRouter, offline-first behavior, service-worker precaching, and update semantics;
5. compare before/after minified, gzip, and PWA precache sizes;
6. run the full web-release verification gate;
7. avoid merely increasing `chunkSizeWarningLimit` unless evidence shows the current bundle structure is intentional and acceptable.

## Scope boundary

WORK-007 records this gap only. It does not implement bundle splitting, dependency changes, or performance optimization.
